我们先为项目添加了一项小功能，但更复杂的更改需要更完善的流程。GitHub Copilot app 支持组织现有的工作流程，帮助我们用正确的方法构建所需功能。从本课开始，你将通过几节课遵循典型的代理驱动开发流程：先使用 issue 生成新功能，确认代码有效且功能行为符合预期，最终将更改成功合并到项目中。

> [!NOTE]
> 后续功能工作流会继续使用同一会话。通常，不同类型的文件会使用不同会话或 PR，但这里会采用简化方式，以便专注于核心概念。

本课将介绍如何：

- 从 GitHub issue 启动新的代理会话；
- 在 **Plan** 模式中定义需求；
- 使用 **Autopilot** 模式实现新功能；
- 审查代码；
- 在浏览器画布中手动验证功能。

继续开发该功能时，你还会更新存储库指令、自定义现有的 `quality-checks` 技能、添加 MCP 验证、创建 QA 代理并创建功能 PR。

## 场景

Tailspin Toys 的目录不断扩展，访问者需要按类别和发行商筛选游戏。待办 issue 已描述该功能，但多个类别如何组合等细节需要在编码前确定。你将使用 Plan 模式解决这些问题，然后授权 Autopilot 执行范围明确的实现。

## 背景

将 AI 编码代理引入开发流程不会改变基本原则。事实上，这些原则反而更加重要！大多数开发人员都会遵循类似的流程：

1. 打开已提交的 issue，查看需要完成的工作详情。
2. 为需要构建的内容制定计划。
3. 构建并审查代码。
4. 运行测试以验证代码。
5. 手动验证新功能。
6. 创建拉取请求 (PR)。
7. 代码通过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数流程都与上述步骤类似。

坚持这种标准方法，可以确保 AI 生成的代码满足既定要求，并经过与手写代码相同的审核流程。

## 会话模式

**会话模式**控制代理的自主程度。你可以从提示框下方的下拉菜单中设置模式，也可以随时更改：

- **Interactive**：你与代理协同工作。代理提出更改建议，并等待你的输入后再继续。
- **Plan**：代理先制定计划。你审查并批准计划后，代理才会执行。
- **Autopilot**：代理完全自主工作，包括编写代码、运行测试和迭代，无需等待输入。

先进入 Plan 模式并审查计划，然后使用 Autopilot 实现计划。

## 从 issue 启动会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 已更新。

1. 在侧边栏的 **Sessions** 下，选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是已有的模板 issue，无需再创建一个。
2. 选择 **New session**，并选择基于更新后 `main` 的**新工作树**。

    ![GitHub Copilot app 中的 issue 视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认 issue 已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让代理运行 `node --version` 和 `npm --version`。如果它们在终端中可用，但在会话中不可用，请检查应用的 PATH 或版本管理器设置，然后完全退出并重新打开应用。重试失败的操作和检查；不要只因为代理找不到 npm 就重新安装 npm。

## 规划筛选功能

规划能让你在 Copilot 编写代码前审查方案。由于会话从 issue 启动，Copilot 已获得功能请求的上下文。发送：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并对照 issue 的验收标准审查计划。确认计划涵盖类别和发行商筛选、无障碍控件、数据访问更改及测试。讨论尚不明确的行为，例如多个类别如何组合，或没有游戏符合条件时如何处理。

计划应使用项目现有工具执行 lint、单元测试、E2E 测试和类型检查。将范围限定为筛选功能的实现和测试；完成质量工作流程后再创建 PR。批准前先要求修改不符合要求的计划内容，并保留 issue URL 和已达成共识的澄清内容，供后续验证使用。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中的等效选项。不要假设批准计划会自动切换模式；请确认模式指示器显示 **Autopilot**。

Copilot 会开始实现功能！你会看到它按既定计划逐步推进、生成代码并运行测试。

> [!NOTE]
> 批准后可能会立即开始实现，因此请先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，请先解决设置问题，再将检查视为已完成。只停止自己启动的服务器。

## 审查并验证实现

代码生成后，和其他代码一样，合并前需要审查。现在检查代码并运行网站，确认一切正常。

1. 打开 **Changes**，检查筛选功能实现和测试。
2. 对照 issue 和已批准的澄清内容检查结果，包括多个类别和发行商组合。确认更改符合现有存储库指令。
3. 检查 lint、单元测试、E2E 测试和类型检查的输出。跳过的检查不能算通过。
4. 接受实现前，解决失败项并重新运行受影响的检查。Playwright 的 E2E 配置会构建并提供预览服务，而且可能复用本地服务器；确认被测服务器属于此工作树，而不是之前课程启动的服务器。

## 体验新功能

代码看起来没问题，但运行正常吗？像之前一样启动应用，并在浏览器画布中打开网站。

1. 使用以下提示，让 Copilot 启动应用并在浏览器画布中打开页面：

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择一个类别并确认结果符合类别条件。清除筛选器，再选择一个发行商并确认结果符合发行商条件。
4. 组合类别和发行商筛选条件，并对照 issue 和已批准的计划检查结果。如果支持多个类别，还要验证已约定的组合行为。
5. 测试一个没有匹配游戏的筛选组合并检查空状态。清除或重置筛选器，确认完整列表重新显示。
6. 完成后，使用以下提示让 Copilot 停止为此会话启动的开发服务器并关闭浏览器画布：

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 为后续课程保留此会话

暂时不要创建或合并筛选功能 PR。请在第 4 到第 8 课中继续使用此会话、工作树和分支。接下来会将自定义指令应用于筛选代码，然后添加技能和 QA 改进，再在第 8 课中创建并合并组合 PR。停止开发服务器后，可以让会话保持空闲；下一课继续使用相同会话。

你使用不同的代理模式构建并审查了功能。本课中，你：

- 从 GitHub issue 启动新的代理会话；
- 在 **Plan** 模式中定义需求；
- 使用 **Autopilot** 模式实现新功能；
- 审查了代码；
- 在浏览器画布中手动验证了功能。
